> 本手册是可照做的步骤清单，配套仓库根目录的 `docker-compose.yml`、`.env.example`、`scripts/` 与 `n8n/` 工作流 JSON。所有 `<...>` 占位符替换为你的真实值。
> 项目背景与功能介绍见 [`项目介绍说明.md`](项目介绍说明.md)；本手册只讲"怎么部署"。

## 0. 实施前准备（先把密钥备齐）

| 密钥 / 值 | 获取方式 | 用到哪里 |
|---|---|---|
| **QQ 授权码** | QQ 邮箱网页版 → 设置 → 账户 → 开启 IMAP/SMTP → 短信获取 16 位码 | Vikunja + ezBookkeeping 邮件 |

## 1. 安全整改（P0，第一步必须做）

1. 登录路由器（<路由器IP>）→ **撤掉群晖的 DMZ 主机设置**。
2. 端口转发：仅添加两条
   - `WAN:80 → <群晖内网IP>:80`
   - `WAN:443 → <群晖内网IP>:443`
3. 群晖 → 控制面板 → 安全性 → 防火墙 → 新建规则：WAN 入站**仅允许 80/443**，其余拒绝。
4. 群晖 DSM 管理端口（5000/5001）**不要**做转发，远程管理走 VPN 或内网。

**额外防火墙（同样重要）**：
- 本项目的 **NPM 管理口 81**、**ddns-go 管理口 9876** 应限制为**仅局域网（<局域网网段>）**可访问，不要对 WAN 开放。
- 本项目端口（80/443/81/9876 + 内部 3456/8080/5678）需与同机其它容器确认不冲突。

> 理由：外网只放行 80/443，三应用都只在 Docker 内部网络，由 NPM 反代，避免全端口裸奔公网。

## 2. docker-compose.yml（以仓库根目录为准）

完整、可直接用的 `docker-compose.yml` 在**仓库根目录**。它全部用环境变量驱动（`.env`，由 `.env.example` 复制而来），运行时数据统一落在 `./data/` 下。本节不再内嵌重复示例，避免与根目录 compose 漂移——**一切以根目录 `docker-compose.yml` 为准**。

关键约定（务必与根目录 `docker-compose.yml` 保持一致）：
- 所有镜像版本锁定在 `.env.example` 的 `*_VERSION` 变量，compose 用 `${XXX_VERSION}` 引用（如 `NPM_VERSION`、`VIKUNJA_VERSION`、`EZB_VERSION`、`N8N_VERSION`、`DDNS_VERSION`）；
- 卷路径统一为 `./data/<服务>/...`，备份暂存目录为 `./data/backup_staging`（容器内挂 `/backup`）；
- Vikunja 已配 `VIKUNJA_SERVICE_PUBLICURL` 对外访问地址（影响邮件链接 / CalDAV 客户端发现 / 跨域白名单）；
- ezBookkeeping 已显式 `EBK_SECURITY_ENABLE_REGISTER=false` 关闭公开注册（其默认 `enable_register=true`，不关则他人可自建账号）；
- NPM 管理后台 `81:81` 仅内网，勿对公网 / WAN 暴露。

首次启动（在仓库根目录执行）：
```bash
cp .env.example .env   # 然后填好真实值（含镜像版本）
mkdir -p data/npm/data data/npm/letsencrypt data/ddns-go \
         data/vikunja/files data/vikunja/db \
         data/ezbookkeeping/data data/ezbookkeeping/storage \
         data/n8n data/backup_staging
chown -R 1000:1000 data/ezbookkeeping/data data/ezbookkeeping/storage
docker compose up -d
```

验证内网可达：`http://<群晖内网IP>:3456`（Vikunja）、`http://<群晖内网IP>:8080`（ezBookkeeping，容器未映射故需临时 `docker exec` 或用 NPM 前先 `curl`）、`http://<群晖内网IP>:5678`（n8n）、`http://<群晖内网IP>:9876`（ddns-go）、`http://<群晖内网IP>:81`（NPM 管理）。

> ezBookkeeping 不在宿主机映射端口，临时想直连排错可临时加 `- "8080:8080"` 或 `docker exec -it ezbookkeeping wget -qO- http://localhost:8080`。

## 3. ddns-go 配置（Namecheap）

1. 浏览器开 `http://<群晖内网IP>:9876`。
2. **DNS 服务商** 选 `Namecheap`。
3. **密码** 填 Namecheap 的 **Dynamic DNS Password**（Namecheap → Domain List → 你的域名 → Advanced DNS → 底部 Dynamic DNS → Enable 后复制）。
4. **Domains** 填：`tasks.yourdomain.com,fin.yourdomain.com,flow.yourdomain.com`（逗号分隔）。
5. ⚠️ **IP 获取方式务必选「接口 / Interface」**（取公网 IP）。选「网卡」会取到内网 IP 导致外网不通。
6. 保存 → 日志显示 `good` 即成功，此后自动维护三条 A 记录。

> Namecheap 侧需预建 3 条 A 记录（类型 `A + Dynamic DNS Record`，IP 先填 `1.2.3.4`，ddns-go 会覆盖）：`tasks` / `fin` / `flow`。

## 4. NPM 反向代理 + Let's Encrypt

1. 开 `http://<群晖内网IP>:81` → 默认 admin@example.com / changeme，立即改密码。
2. **Proxy Hosts → Add Proxy Host**，建 3 条：

| 域名 | Forward Hostname / IP | Forward Port | SSL | 备注 |
|---|---|---|---|---|
| `tasks.yourdomain.com` | `vikunja` | `3456` | 选 Let's Encrypt，Force SSL | 默认 |
| `fin.yourdomain.com` | `ezbookkeeping` | `8080` | 选 Let's Encrypt，Force SSL | 默认 |
| `flow.yourdomain.com` | `n8n` | `5678` | 选 Let's Encrypt，Force SSL | **开 Basic Auth**（Details 页 → 设账号密码）|

3. SSL 证书：每条约主机 → SSL 选项卡 → 选 `Request a new SSL Certificate` → 填邮箱、勾 `Use a DNS Challenge` **不需要**（HTTP-01 即可，因为 80 已转发）→ 选 `Force SSL` + `HTTP/2 Support`。
   - Let's Encrypt 用 HTTP-01，需 80 端口可达（已转发）。
4. 验证：`https://tasks.yourdomain.com`、`https://fin.yourdomain.com`、`https://flow.yourdomain.com` 均锁标可访问。

### 4.1 证书策略
- **推荐：Let's Encrypt 自动续期（零维护）**。NPM 申请的是 90 天证书，**默认在到期前约 30 天自动续期**，全程无需手动申请/替换。只要 80 端口保持转发，续期自动发生。建代理主机时勾一次「Force SSL + 申请证书」即可，**以后不用管**。
- **备选：自签证书**。若以后想完全离线/内网，可在 NPM 用「Custom Certificate」上传自签证书。注意：**自签证书在手机原生 App（尤其 ezBookkeeping App）会报证书不信任**，需在每台设备安装/信任根证书，且自签通常 1 年有效期也需手动更换。
- 结论：本方案默认采用 **Let's Encrypt 自动续期**，无周期性替换动作。

> `flow.` 后台建议：NPM Basic Auth **+** 仅内网/VPN 访问；n8n 自身首次登录设 Owner 强密码。

## 5. 应用初始化

### 5.1 Vikunja
1. 开 `https://tasks.yourdomain.com` → 注册管理员账号。
   - ⚠️ 因 compose 已设 `VIKUNJA_SERVICE_ENABLEREGISTRATION: "false"`，若页面无注册入口（关闭公开注册后首屏可能只显示登录），用 CLI 建首个管理员：
     ```bash
     docker exec -it vikunja /app/vikunja/vikunja user create --username admin --email <管理员QQ邮箱>@qq.com --password '<强密码>'
     ```
   - 数据库为空时通常仍允许创建第一个用户；若注册页确实不可用，以上 CLI 是兜底。
2. 设置 → **API Tokens** → 新建，复制 token（形如 `tk_xxx`），稍后填入 n8n 变量 `vikunja_token`。
3. 创建结构：**Namespace（类别）** → **Project（项目）** → **Task（任务）**。
4. 任务标签约定（Path A 标签编码）：
   - `fund:5000:CNY` — 所需资金（金额:币种）
   - `res:服务器` / `res:设计` — 所需资源（可多个）
   - `deliv:验收报告` — 交付物
   - `milestone` — 标记为里程碑任务
5. 任务内设置 `start date` / `end date` / `due date` 与**提醒（Reminder）**（临期/到期邮件由 Vikunja 经 QQ SMTP 发送）。

### 5.2 ezBookkeeping
1. 开 `https://fin.yourdomain.com` → 注册账号（首个即管理员，即资金池账号；凭据由多人共用，见 §5.4）。
2. 用户设置 → 安全 → 生成令牌（API Token，形如长串），复制，填入 n8n 变量 `ezb_token`。
3. 建**账户**：只建「**现金**」「**存款**」两个，记下账户 ID（接口或页面 URL 中取），分别填 `ezb_account_cash_id` / `ezb_account_deposit_id`。
4. 建**交易分类**（一级=项目名；二级=用途，如「服务器采购」）。另建专用分类「**贷款还款**」填 `ezb_cat_loan`。记下用于支出的分类 ID，填 `ezb_cat_expense`；如需收入另记 `ezb_cat_income`。
5. 可选：建**标签**对应各项目名，便于统计。
6. 验证邮件：用户设置 → 发一封测试邮件（或创建一笔带提醒的交易）。
7. ⚠️ **公开注册默认已关闭**：`docker-compose.yml` 已设 `EBK_SECURITY_ENABLE_REGISTER=false`（ezB 默认 `enable_register=true`，不关则他人可自建账号）。如需临时开放注册，把该变量改为 `true` 后 `docker compose up -d` 即可；ezB 的 CLI 不提供 `set-setting` 子命令，勿用 `docker exec ... userdata set-setting` 方式操作。

### 5.3 n8n 变量（桥接键）
n8n 顶部 → **Settings → Variables** 添加：
- `vikunja_token` = `tk_xxx`
- `ezb_token` = `<ezB API Token>`
- `ezb_account_cash_id` = `<资金池「现金」账户 ID>`（默认支出账户）
- `ezb_account_deposit_id` = `<资金池「存款」账户 ID>`（贷款还款等走银行卡/存款用）
- `ezb_cat_expense` = `<支出分类 ID>`
- `ezb_cat_loan` = `<「贷款还款」分类 ID>`（定期扣款专用）
- （可选）`ezb_cat_income` = `<收入分类 ID>`
- （可选，但**本方案不启用**）`webhook_secret`：Vikunja Webhook 支持 HMAC-SHA256 签名头 `X-Vikunja-Signature`，但 **n8n 1.x 的 Webhook 节点不校验该签名**。本方案 webhook 走 Docker 内网 `http://n8n:5678`，不经过公网，故**不要填 secret**——既避免「以为有保护实则无」的错觉，也避免文档/脚本里出现无对应校验的悬空字段。

> 注：QQ 邮箱仅用于系统提醒（Vikunja / ezBookkeeping 的临期/到期邮件），已在各自 docker-compose 环境变量里配置；备份改用「写入群晖共享」方式（见 §9），不再经邮件，故此处无邮件变量。

### 5.4 多用户与权限
- n8n 是内部自动化服务，用单个 Owner 账号即可，不算"用户"。
- ⚠️ **财务"多人共享一个资金池"在 ezBookkeeping 存在硬性限制**：开发者已明确（GitHub issue #53），ezBookkeeping 每个用户的账户/分类/标签都绑定该用户，**不支持跨用户共享账户，且无计划支持**。因此本方案采用如下模型：
  - **任务系统（Vikunja）= 3 个用户，其中 1 人兼管理员**（身份/权限在任务侧管理）。
  - **财务系统（ezBookkeeping）= 1 个共享账号 = 资金池**。多人都用**同一套 ezB 登录凭据**访问这个共享资金池（谁记的账可在交易备注里写明以区分）；n8n 桥接也用这一个账号的 Token，把所有任务的预算/支出统一记进该池。
  - 这是 ezBookkeeping 现有能力下实现"多人共享一个资金池"的**唯一可行方式**。若坚持要 3 套独立财务账本，则无法满足"共享资金池"，需退回 Firefly III（其天然多用户 + 共享账本）。

**Vikunja（任务系统，3 用户 / 1 管理员）**
- 首个注册用户 = **管理员**（即 3 人里兼管理员的那位）。注册前确保 `VIKUNJA_SERVICE_ENABLEREGISTRATION: "false"`（docker-compose 已设）以关闭公开注册。
- 管理员加另外 2 个普通用户：**Admin 面板 → Users → Add New User**（用户名/邮箱/密码），无需重开注册。
- 项目/命名空间共享给这 3 个用户并设权限（读/写/管理）。
- 邮件提醒按各用户自己的邮箱发送，每人需填真实邮箱。

**ezBookkeeping（财务系统，1 个共享资金池账号 + 操作人标记）**
- 首个注册用户 = **该资金池的管理员账号**（建议就用上面那位兼管理员的人）。注册时勾选启用预设分类。
- **不开 2FA**。
- 其余人不单独建 ezB 账号，直接共用这个共享账号的登录凭据来查看/录入资金池——即「分 3 个账户只为记录方便，后台用 1 个共享账号」的落地方式。
- **操作人标记（关键）**：为区分"谁记的账"，所有经人在 ezB 手动录入的交易，在**交易备注/评论**里统一加前缀 `by:<用户名>`（如 `by:小明`）；由 n8n 自动记账的任务（预算/支出）则在备注里写 `by:n8n(#vk-<taskID>)`。这样共享池里也能追溯到人。
- 资金池账户（**只设两大类**）：建「**现金**」「**存款**」两个账户即可，记下账户 ID 分别填 `ezb_account_cash_id` / `ezb_account_deposit_id`。
  - **默认记账账户 = 现金**（任务支出、一般开销走现金）。
  - **贷款还款走「存款」**（房贷/车贷从银行卡扣，对应存款账户）。通过在任务的 `fund:` 标签里指定账户（见 §5.5）来控制取哪个账户。

> 用户口径小结：**任务侧 3 人（1 管理员 + 2 普通，各用各自账号，便于任务分派与按人邮件提醒）**；**财务侧 1 个共享资金池账号，靠 `by:用户名` 标记区分操作人**；n8n 单 Owner。

### 5.5 预算登记口径
ezBookkeeping **没有独立的"预算/计划"对象**，只有交易。因此用如下建模：
- **任务创建时（`task.created`）** → n8n `vikunja-budget-plan` 在 ezB 记一笔**计划支出**交易：分类=对应项目、标签=`plan`、评论=`计划-#vk-<taskID>`、金额取自任务 `fund:` 标签。代表"这笔任务的预算已登记"。
- **任务完成时（`task.updated`+`done=true`）** → n8n `vikunja-task-sync` 在 ezB 记一笔**实际支出**交易（标签=`done`、评论=`#vk-<taskID>`）。
- 两笔都挂在同一个共享资金池下，金额单位均为**分**（`¥50.00`→`5000`）。在 ezB 里按 `#vk-` 与 `plan`/`done` 标签即可区分"计划 vs 实际"，做偏差分析。
- ⚠️ **`vikunja-budget-plan` 必须跳过带 `recur` 标签的任务**：Vikunja recurring 任务每完成一次会生成新的任务实例（触发 `task.created`），若不过滤就会每月在 ezB 重复记一笔"计划支出"，与 ezB 周期交易重复。工作流里加 IF 节点：标签含 `recur` 则直接结束（不记账）。

**`fund:` 标签约定（含账户维度）**：
```
fund:<金额(元)>:<币种>[:<账户>]
```
- 账户取值：`cash`（现金，默认）/ `deposit`（存款）。省略时默认 `cash`。
- 示例：`fund:5000:CNY`（¥5000 现金）、`fund:3800:CNY:deposit`（¥3800 从存款扣，用于贷款还款）。
- n8n 按账户值选 `ezb_account_cash_id` 或 `ezb_account_deposit_id`。

### 5.6 定期扣款项（贷款还款）
需要一个**定期自动扣款**入口，主要用于「贷款还款」（房贷/车贷等）。设计要点：**财务侧为自动扣款权威来源，任务侧只做跟踪，贷款不提醒**。

**A. 财务侧（ezBookkeeping，自动扣款的权威来源）**
- 在 ezB 建一笔**周期交易（自动交易）**：分类=`贷款还款`（填 `ezb_cat_loan`）、账户=`存款`（`ezb_account_deposit_id`）、金额=月供、周期=**每月**。
- ezB 会**按周期自动过账**，资金池「存款」每月自动扣减，无需手动、不依赖任务系统。
- ⚠️ **该周期交易不要开启 ezB 自身的提醒**（贷款不提醒）：建周期交易时留空提醒/通知。
- **额度随时可调**：直接在 ezB 改这笔周期交易的金额即可，不必动任务侧；任务侧只跟踪、不控制钱。
- 不拆分：只建一个「定期扣款」入口，不按房贷/车贷再分子项，金额随你调整。

**B. 任务侧（Vikunja，仅跟踪，不提醒、不记账）**
- 在 Vikunja 建一个专门项目 **「定期扣款」**，里面放一笔 recurring 任务代表当月扣款。
- 每个任务设：
  - 到期日=当月还款日 + **重复规则**（Vikunja 原生 recurring 任务：`repeat_after` 按秒，每月≈`2592000`；或界面选"每月重复"）。
  - 标签：`recur`、`fund:<月供>:CNY:deposit`、`#recur-<标识>`。
  - **⚠️ 不设置任何 Reminder（贷款不提醒）**：既无 Vikunja 邮件提醒，也无 CalDAV 闹钟。任务仅作为日历上的"到期日条目"用于**跟踪**。

**C. 防重复记账（关键）**
- 既然 ezB 周期交易已自动过账，**n8n 不再为 `recur` 标签的任务触发支出记账**（避免和 ezB 周期交易重复扣）。
- 反过来：n8n `ezbookkeeping-poll` 在拉到带 `#recur-<标识>` 的 ezB 周期过账记录后，**自动把对应 Vikunja 那个月份的 recurring 任务标记为已完成**（回写评论 `by:ezB周期交易 已扣款 ¥X`），实现"财务扣了 → 任务自动勾掉"的闭环。
- 桥接键：Vikunja 任务的 `#recur-<标识>` 标签 = ezB 周期交易评论里的 `#recur-<标识>`。

> 结论：「贷款还款」= **ezB 每月自动真扣钱 + Vikunja 仅跟踪（无提醒、无重复记账）**。其他一次性任务（含临时提前还款）作为普通任务走 §5.5 正常记账 + 正常提醒。

### 5.7 提醒设置
**核心原则**：除「贷款/定期扣款」外，所有任务的**临期/到期提醒由你按任务手工设定提前量**，并通过 **CalDAV 同步进手机系统提醒**（见 §8.1），不依赖邮件也能在手机弹提醒。

- **每任务独立设定提前量（Vikunja 原生）**：在每个任务里加 Reminder，可设"到期前 N 天/小时"或绝对时间；不同任务填不同值即可实现"按任务手工设定"。
- **按项目区分**：Vikunja 没有"项目级默认提醒"开关，但提醒是跟着任务的——给某项目下的任务统一设一个提前量，就等价于"该项目用这个提醒节奏"；不同项目设不同值即可分别控制。
- **手机系统提醒（CalDAV）**：任务及到期日经 CalDAV 同步到手机日历/提醒 App（§8.1），手机上的系统提醒即由此覆盖。Vikunja 自身的邮件提醒作为**兜底**（断网/未配 CalDAV 时仍能收到），二者可并存。
- **贷款不提醒**：「定期扣款」项目下的 recur 任务不设 Reminder（§5.6 B），手机也不会弹其闹钟，仅做日历跟踪。
- **可调**：随时改任务的 Reminder 提前量即时生效，无需改配置。

## 6. Vikunja Webhook 配置（触发 n8n，走内网）

在 Vikunja 里为每个需要桥接的项目建 Webhook（UI 或 API 二选一）：

**方式 A（UI）**：项目 → 设置 → Webhooks → 新建**两个** Webhook：
- **Webhook-1（任务完成→记账）**：Target URL=`http://n8n:5678/webhook/vikunja-task`，Events 勾 `task.updated`，Secret 不填（webhook 走内网，n8n 不校验签名）。
- **Webhook-2（任务新建→预算）**：Target URL=`http://n8n:5678/webhook/vikunja-plan`，Events 勾 `task.created`，Secret 不填（webhook 走内网，n8n 不校验签名）。
- 两个分别保存。

**方式 B（API，curl 示例）**：
> **项目 ID 取得方法**：在 Vikunja 网页打开目标项目，浏览器地址栏形如 `https://tasks.<域名>/projects/<id>/...`，其中 `<id>` 即项目 ID；或用 `GET https://tasks.<域名>/api/v1/projects`（带 `Authorization: Bearer <vikunja_token>`）列出全部项目取其 `id` 字段。
> **关于 secret**：本方案 webhook 走 Docker 内网、不经公网，且 n8n 1.x 不校验 Vikunja 的 HMAC 签名，故下方 curl **不传 `secret` 字段**。

```bash
# Webhook-1：任务更新（完成/改动）
curl -X PUT "https://tasks.yourdomain.com/api/v1/projects/<PROJECT_ID>/webhooks" \
  -H "Authorization: Bearer <vikunja_token>" \
  -H "Content-Type: application/json" \
  -d '{"target_url":"http://n8n:5678/webhook/vikunja-task",
       "events":["task.updated"]}'

# Webhook-2：任务新建（登记预算）
curl -X PUT "https://tasks.yourdomain.com/api/v1/projects/<PROJECT_ID>/webhooks" \
  -H "Authorization: Bearer <vikunja_token>" \
  -H "Content-Type: application/json" \
  -d '{"target_url":"http://n8n:5678/webhook/vikunja-plan",
       "events":["task.created"]}'
```
> **满足内部通信不走外网**：Webhook 目标用 Docker 内部地址 `http://n8n:5678`，Vikunja 与 n8n 在同一个网络上直接通信，**不经过公网/域名/DNS**。即使外网断或域名未生效，桥接照常工作。
> 注意：Vikunja **没有**独立的 `task.completed` 事件。任务完成表现为 `task.updated` 且 `done=true`，n8n 工作流里用 IF 节点判定。

## 7. n8n 工作流（4 个，可导入 JSON 见同目录 `n8n/`）

| 文件 | 名称 | 触发 | 作用 |
|---|---|---|---|
| `n8n/vikunja-task-sync.json` | 任务→财务（核心） | Vikunja Webhook | 解析 `fund:` 标签；任务完成时自动在 ezB 记**实际支出**，并回写 Vikunja 评论 |
| `n8n/ezbookkeeping-poll.json` | 财务→任务 | 定时（每 5 分钟） | 拉取含 `#vk-<任务ID>` 的新交易，回写对应 Vikunja 任务评论 |
| `n8n/vikunja-budget-plan.json` | 建账计划 | Vikunja Webhook(`task.created`) | 任务新建时把 `fund:` 金额登记为 ezB **计划支出（预算）** |
| `n8n/ezbookkeeping-bill-reminder.json` | 账单临期提醒 | 定时（每日） | 查 ezB 周期/计划交易临期，经邮件提醒（模板，**必须排除 `ezb_cat_loan` 贷款分类**，因贷款不提醒；默认建议保持禁用，按需启用） |

> **备份不再用 n8n 工作流**，改由群晖任务计划跑宿主机脚本 `scripts/backup.sh`（详见 §9）：原生全量导出（Vikunja `dump` ZIP + ezB 数据库文件）+ 高压缩（7z/xz）+ 写入群晖共享 + 仅保留最近 3 份。早期仓库里的 `n8n/backup-csv-7z-email.json` 备份工作流已从仓库移除，备份完全由 `scripts/backup.sh` 承担。

**导入方法**：n8n → Workflows → 右上 **Import from File** → 选对应 JSON。导入后：
- 在 **Settings → Variables** 确认第 5.3 节变量已设。
- `vikunja-task-sync` / `vikunja-budget-plan` 的 Webhook 路径需与第 6 节 Vikunja Webhook 的 Target URL 一致（`/webhook/vikunja-task` 与 `/webhook/vikunja-plan`）。
- 各 HTTP Request 节点用的是**容器内部地址**（`http://vikunja:3456`、`http://ezbookkeeping:8080`），走 Docker 内部网络，无需 TLS。
- 启用（Active）工作流。

### 桥接数据约定（务必两边一致）
- **桥接键**：Vikunja 项目名 = ezBookkeeping 分类(一级) = 交易 Tag。
- 金额单位：ezB 交易 `sourceAmount` 是**分**（如 ¥50.00 → `5000`）。n8n 里用 `Math.round(amount*100)`。
- 中国时区：`utcOffset = 480`。
- **账户选择**：`fund:` 标签的 `:账户` 维度（`cash`/`deposit`）决定 n8n 选 `ezb_account_cash_id` 或 `ezb_account_deposit_id`（§5.5）。
- 任务→财务的回写：n8n 在 ezB 交易评论里写入 `#vk-<任务ID>`，这样 `ezbookkeeping-poll` 能把财务侧后续变动准确回贴到原任务。
- **定期扣款闭环键**：`#recur-<标识>` 同时写在 Vikunja recur 任务标签与 ezB 周期交易评论里；`ezbookkeeping-poll` 拉到带 `#recur-` 的过账后，自动把对应 Vikunja 任务标完成（§5.6）。`recur` 标签任务**不触发** n8n 支出记账，避免与 ezB 周期交易重复。

## 8. 移动端
- Vikunja：手机浏览器开 `https://tasks.yourdomain.com` → 加主屏 PWA；或用 **CalDAV** 接系统提醒/Apple Reminders / Tasks.org（见下）。
- ezBookkeeping：应用商店装官方 App（Android/iOS）→ 登录地址填 `https://fin.yourdomain.com`。

### 8.1 Vikunja CalDAV
Vikunja **原生支持 CalDAV**（无需额外容器），把任务/到期日同步到手机日历或提醒 App，实现"临期/到期"在手机系统层也弹提醒。配置：
- **CalDAV 地址（服务器 URL）**：`https://tasks.yourdomain.com/dav/<用户名>/<日历key>`
  - `<用户名>` 即 Vikunja 登录名；`<日历key>` 在 Vikunja Web → 用户设置 → **CalDAV/卡片** 里查看（每个用户有自己的 key，互不通用）。
  - iOS/macOS「添加 CalDAV 账户」、Android「Tasks.org / 日历」均填此 URL + Vikunja 用户名密码。
- **前提**：必须 **HTTPS**（§3/§4 已配），CalDAV 在 HTTP 下客户端通常拒绝。
- **覆盖范围**：任务标题、到期日、重复规则（含「定期扣款」recurring 任务）都会同步到手机日历/提醒 App。
- **手机系统提醒**：任务经 CalDAV 同步后，手机系统提醒由对应日历/提醒 App 接管。你在 Vikunja 任务里设的 **Reminder 提前量（§5.7）** 决定手机什么时候弹提醒；不同任务设不同提前量，手机也就分别提醒。这是除 Vikunja 邮件之外的手机端提醒通道。
- **贷款不弹闹钟**：「定期扣款」项目的 recur 任务**不设 Reminder**（§5.6 B），因此 CalDAV 同步到手机后只有"到期日条目"、不触发闹钟——满足"贷款不提醒、仅跟踪"。
- **注意**：CalDAV 主要是**日历/任务订阅式**同步（多数客户端只读任务到日历，改状态仍用 Vikunja App/PWA）；提醒闹钟的实际触发由手机日历 App 处理，Vikunja 邮件提醒作为兜底并存。ezBookkeeping **无 CalDAV**，财务只在 ezB App 内看。
- 群晖防火墙需放 `443`（已转发），CalDAV 走 443 经 NPM 反代到 `vikunja:3456`。

## 9. 备份（原生全量导出 → 高压缩 → 群晖共享，仅留 3 份）

### 9.0 备份源选型
| 系统 | 全量备份方式 | 可用性 | 可恢复性 | 易读性 | 结论 |
|---|---|---|---|---|---|
| **Vikunja** | `vikunja dump` → ZIP（含 `vikunja.db` SQLite + `files/` 附件 + 配置/版本） | ✅ 官方一条命令 | ✅ `vikunja restore <zip>` 完整还原 | ⚠️ db 需 SQLite 查看器；附件为原始文件 | **采用为主备** |
| **ezBookkeeping** | 直接拷数据库文件（卷 `ezbookkeeping/data/*.db`，SQLite） | ✅ 文件级拷贝 | ✅ 挂回该 db 即恢复 | ⚠️ SQLite，非人读 | **采用为主备** |
| ezBookkeeping（辅助） | API 导出 CSV/OFX（`GET /api/data/export.csv`，需 `EBK_DATA_ENABLE_EXPORT`） | ✅ | ⚠️ 仅数据，不含全部设置 | ✅ 人可直接读/再导入 | 作为"人读辅助备份"纳入压缩包 |

> 结论：**主备用「原生全量」（Vikunja dump ZIP + ezB 数据库文件）**，保证一键还原；**辅以 ezB 的 CSV 导出**放进同一个压缩包，方便人直接看账。

### 9.1 主备份：群晖任务计划脚本
脚本已写入 `scripts/backup.sh`，在群晖「控制面板 → 任务计划 → 用户自定义脚本」建一个**每周日 03:00** 的任务，命令填 `bash /volume1/docker/taskfin/scripts/backup.sh`。脚本逻辑：
1. **Vikunja 全量**：`docker exec vikunja /app/vikunja/vikunja dump --path /backup` → 在 `backup_staging/`（容器内 `/backup`）生成 `vikunja-<时间戳>.zip`（`dump` 由 `--path` 决定落盘位置、不读当前目录，故无需 `cd /backup`）。
2. **ezB 数据库**：`cp ezbookkeeping/data/*.db backup_staging/`。
3. **ezB 人读 CSV**（可选）：脚本内用 `docker exec ezbookkeeping wget -qO- 'http://localhost:8080/api/data/export.csv?utcOffset=480' --header='Authorization: Bearer <token>'` 取数据写入 `backup_staging/ezbookkeeping.csv`（ezB 未映射主机端口，故走容器内访问）。
4. **高压缩**：优先 `7z a -t7z -mx=9`（LZMA2 最高压缩率）；若系统无 `7z`，自动退回 `tar -cJf`（xz，-9）；再无则 `tar -czf`（gzip）。产物 `taskfin-backup-<时间戳>.7z|.tar.xz|.tgz`。
5. **写入群晖共享文件夹**：拷到共享文件夹 `/volume1/share/taskfin_backup`（本地路径按你群晖实际挂载，需先在 DSM「控制面板→共享文件夹」建好子目录 `taskfin_backup`；Windows 资源管理器即 `\\<群晖内网IP>\share\taskfin_backup`，可直接访问）。脚本顶部 `SMB_DIR` 已设为 `/volume1/share/taskfin_backup`，若你的共享名/卷不同请改该变量。
   - 若你要备份到**另一台机器**的 Windows 共享：在脚本顶部把 `SMB_DIR` 改成 cifs 挂载点（群晖 `控制面板 → 文件服务 → 挂载 CIFS` 挂载后填其路径），其余不变。
6. **仅保留最近 3 份**：对 `/volume1/share/taskfin_backup/` 里 `taskfin-backup-*` 按修改时间排序，删掉第 4 份及更旧的。

> 压缩工具可用性：群晖 DSM 默认未必带 `7z`。为获得最高压缩率，建议从**套件中心装「7-Zip」**（SynoCommunity）后再跑；脚本已做降级（无 7z → xz → gzip），不装也能备份，只是压缩率略低。

### 9.2 还原方法
- **Vikunja**：`docker exec -i vikunja /app/vikunja/vikunja restore /backup/<vikunja-xxx.zip>`（把 zip 放进 `backup_staging/` 再执行；`restore` 只读取 zip 文件、不需要 TTY，故用 `-i` 即可，在群晖任务计划 / 管道等非交互场景 `-t` 会报 "not a TTY" 失败）。
- **ezBookkeeping**：停容器 → 用备份的 `*.db` 覆盖 `ezbookkeeping/data/` 下同名文件 → 起容器。
- **人读核对**：直接打开压缩包里的 `ezbookkeeping.csv`。

### 9.3 兜底：卷级整盘备份（可选）
仍可按需打包整个 compose 目录做冷备（含数据库原文件、NPM 证书、n8n 工作流与变量），同样落 `/volume1/share/taskfin_backup/` 并保留 3 份：
```bash
cd /volume1/docker/taskfin
tar czf /volume1/share/taskfin_backup/taskfin-vol-$(date +%F).tgz npm ddns-go vikunja ezbookkeeping n8n
# 保留最近 3 份
ls -t /volume1/share/taskfin_backup/taskfin-vol-*.tgz | tail -n +4 | xargs -r rm -f
```
> 注意：n8n 的凭证/变量用内置密钥加密，备份 `n8n/` 卷即可在同源恢复；若迁移到别的机器需连同该密钥一并处理。

## 11. 已知约束与注意
- ezBookkeeping 出站 Webhook 弱 → 「财务→任务」方向用 n8n **定时轮询**（已设计）。
- Vikunja 无原生自定义字段 → 资金/资源/交付物用标签编码（Path A），零代码可跑；后续若需真自定义字段需二次开发。
- 里程碑用 `milestone` 标签的特殊任务 + 过滤器汇总，无原生甘特里程碑对象。

- 所有容器间调用走内部域名（vikunja / ezbookkeeping / n8n），不经过公网。
- 🔴 **ezBookkeeping 不支持跨用户共享账户**（开发者确认无计划支持）→ 财务"多人共享一个资金池"以**单一共享 ezB 账号 + `by:用户名` 标记**实现（见 §5.4）。若未来要真多用户独立账本又要共享，须换 Firefly III。
- **备份改为宿主机脚本**（§9），用 `vikunja dump` ZIP + ezB 数据库文件，压缩优先 7z（-mx=9）、否则 xz、再否则 gzip；写入群晖共享 `/volume1/share/taskfin_backup` 并仅留最近 3 份。
- Vikunja 全量备份用官方 `vikunja dump`/`restore`（原生 ZIP，含 DB+附件），比 API 转 CSV 更完整可恢复；ezB 额外导出 CSV 仅作人读辅助。
- ezBookkeeping CSV 导出受 `EBK_DATA_ENABLE_EXPORT` 开关 + 每用户权限限制。
- 按需求**不开 2FA**（§5.4）；如需可在各用户个人设置单独开启。
- 备份不走邮件（§9），改为写入群晖共享 `/volume1/share/taskfin_backup`。

### 11.1 内部通信矩阵（三系统只在群晖内部互通）
本方案所有**服务间**调用均走 Docker 内部网络，不触碰公网/域名/DNS：

| 调用方向 | 地址 | 是否走外网 |
|---|---|---|
| 浏览器/手机 → 三系统 UI | `https://tasks/fin/flow.yourdomain.com`（经 NPM） | 是（用户访问才走） |
| Vikunja → n8n（Webhook） | `http://n8n:5678/webhook/...` | **否，内部** |
| n8n → Vikunja（评论回写/API） | `http://vikunja:3456/api/v1/...` | **否，内部** |
| n8n → ezBookkeeping（记账/查询） | `http://ezbookkeeping:8080/api/v1/...` | **否，内部** |
| ezBookkeeping → n8n | 无（n8n 主动轮询 ezB 内部 API） | **否，内部** |

> 结论：**任务系统、财务系统、自动化桥接三者互相通信全部在群晖内部完成**，与外网无关。外网只用于"你在外用手机/电脑打开网页"。即便断网或 DDNS/证书异常，内部桥接照常运转。

## 12. 部署前核查 / 已知风险

以下为设计阶段尚未在真机验证的项，部署时逐条确认：

### B1. ⚠️ CalDAV 手机闹钟可靠性（最高风险）
- **问题**：方案假设"手机系统提醒由 CalDAV 覆盖"。但 Vikunja 的 CalDAV 可能只同步任务/到期日，**不导出 VALARM（提醒闹钟）**。多数 CalDAV 客户端把任务当日历事件只读，不会自动弹闹钟。
- **影响**：用户期望的"手机系统提醒"可能落空，只剩 Vikunja 邮件提醒兜底。
- **验证方法**：实机配置 CalDAV 到一个手机日历 App，给某任务设 Reminder 提前量，看手机是否真弹通知。
- **兜底**：若不行，可靠提醒仍是 Vikunja 邮件（QQ SMTP）。需在部署时向使用者说明此限制，或改方案（如用 n8n 把 Vikunja 提醒转成手机推送/IM）。

### B2. ⚠️ n8n 4 个 JSON 未实机校验（高风险）
- **问题**：工作流是设计阶段编写，未连真实 API 跑过。可能问题：`fund:` 标签解析逻辑（拆分金额/币种/账户）、金额 ×100（元→分）的取值与四舍五入、ezB 交易 `type`/`categoryId`/`sourceAccountId` 字段名与实机一致、节点 `typeVersion` 与所装 n8n 版本匹配、 `vikunja-budget-plan` 的"跳过 recur"IF 条件。
- **动作**：导入后必须联调；建议先在 n8n 用"执行工作流（手动）"+ 真实 token 逐步跑通，再启用 Webhook/定时。

### B3. 备份共享真实路径（中风险）
- **问题**：DSM 共享文件夹通常挂在 `/volume1/<共享名>`，即真实路径多为 `/volume1/share/backup`；`/share/backup` 可能不存在导致备份脚本写不进。
- **动作**：部署时确认共享真实绝对路径，改 `scripts/backup.sh` 的 `SMB_DIR`（脚本已留注释说明）。

### B4. DSM 上 7z 二进制名（低风险）
- **问题**：脚本优先用 `7z`；若从 SynoCommunity 装 7-Zip，二进制可能叫 `7za`，`command -v 7z` 失败会降级到 xz（仍可用，压缩率略低）。
- **动作**：装好后 `which 7z 7za`；若只有 `7za`，把脚本里 `command -v 7z` 改为 `command -v 7za`，或建软链。

### B5. ezB 周期交易"每月"的准确表达（中风险）
- **问题**：ezB 周期交易重复规则的具体参数（间隔/类型）需实机确认字段；方案写"每月"但没给 ezB 的周期表达式。
- **动作**：在 ezB Web 建周期交易时设置"每月 X 号"，记下参数；若需 n8n 调用 API 建，再补字段映射。

### B6. Vikunja recurring 任务生成新实例的标签继承（中风险）
- **问题**：`ezbookkeeping-poll` 靠 `#recur-<标识>` 标签匹配当月实例并自动勾掉。需确认 Vikunja recurring 完成后生成的新实例**继承**原任务的 `recur` 与 `#recur-<标识>` 标签，否则闭环断裂。
- **动作**：实机建一个 recur 任务，完成一次，观察新实例标签是否保留。

### B7. n8n 内部 URL 与 Webhook 接收（低风险）
- **问题**：Vikunja Webhook 目标 `http://n8n:5678/webhook/...` 依赖 Docker 内网 DNS。若 n8n 容器名或网络名变，需同步改。
- **动作**：保持 compose 中服务名 `n8n`/`vikunja`/`ezbookkeeping` 不变。

## 附录 A：ezBookkeeping 关键 API（n8n HTTP Request 用）
- Base：`http://ezbookkeeping:8080/api/v1`
- 认证头：`Authorization: Bearer <ezb_token>`
- 新增交易：`POST /transactions/add.json`
  请求体：`{"type":3,"categoryId":"<分类ID>","time":<unix秒>,"utcOffset":480,"sourceAccountId":"<账户ID>","sourceAmount":<分>,"tagIds":["<标签ID>"],"comment":"任务完成记账 #vk-<任务ID>"}`
  - `type`：1 余额变更 / 2 收入 / 3 支出 / 4 转账
- 列出交易：`GET /transactions/list.json?count=20`（时间游标分页）
- 新增标签：`POST /transaction/tags/add.json` → `{"name":"项目A"}`
- 新增分类：`POST /transaction/categories/add.json` → `{"name":"项目A","type":2,"parentId":""}`

## 附录 B：Vikunja 关键 API
- Base：`http://vikunja:3456/api/v1`
- 认证头：`Authorization: Bearer <vikunja_token>`
- 建 Webhook：`PUT /projects/<id>/webhooks`
- 任务评论：`POST /tasks/<id>/comments` → `{"comment":"..."}`
- 事件名：`task.created` / `task.updated` / `task.deleted`（完成=updated 且 done=true）
- 签名头：`X-Vikunja-Signature`（HMAC-SHA256，secret 为建 Webhook 时填的串）。⚠️ 本方案 n8n 端**不校验**该签名（节点 `options` 为空），且 webhook 走内网不经公网，建 Webhook 时**不填 secret** 即可，无需处理此头。
