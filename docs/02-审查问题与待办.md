## B. 仍须实机验证的技术不确定性（高风险优先）

### B1. ⚠️ CalDAV 手机闹钟可靠性（最高风险）
- **问题**：方案假设"手机系统提醒由 CalDAV 覆盖"。但 Vikunja 的 CalDAV 可能只同步任务/到期日，**不导出 VALARM（提醒闹钟）**。多数 CalDAV 客户端把任务当日历事件只读，不会自动弹闹钟。
- **影响**：用户期望的"手机系统提醒"可能落空，只剩 Vikunja 邮件提醒兜底。
- **验证方法**：实机配置 CalDAV 到一个手机日历 App，给某任务设 Reminder 提前量，看手机是否真弹通知。
- **兜底**：若不行，可靠提醒仍是 Vikunja 邮件（QQ SMTP）。需在终稿向用户说明此限制，或改方案（如用 n8n 把 Vikunja 提醒转成手机推送/IM）。

### B2. ⚠️ n8n 4 个 JSON 未实机校验（高风险）
- **问题**：工作流是设计阶段编写，未连真实 API 跑过。可能问题：
  - `fund:` 标签解析逻辑（拆分金额/币种/账户）需 Code 节点正确实现；
  - 金额 ×100（元→分）的取值与四舍五入；
  - ezB 交易 `type`/`categoryId`/`sourceAccountId` 字段名与实机一致；
  - 节点 `typeVersion` 与所装 n8n 版本匹配（导入报错需微调）；
  - `vikunja-budget-plan` 的"跳过 recur"IF 条件需正确引用标签数组。
- **动作**：导入后必须联调；建议先在 n8n 用"执行工作流（手动）"+ 真实 token 逐步跑通，再启用 Webhook/定时。

### B3. `/share/backup` 实际挂载路径（中风险）
- **问题**：DSM 共享文件夹通常挂在 `/volume1/<共享名>`，即真实路径多为 `/volume1/share/backup`；`/share/backup` 可能不存在导致备份脚本写不进。
- **动作**：部署时确认共享真实绝对路径，改 `scripts/backup.sh` 的 `SMB_DIR`（脚本已留注释说明）。

### B4. DSM 上 7z 二进制名（低风险）
- **问题**：脚本优先用 `7z`；若从 SynoCommunity 装 7-Zip，二进制可能叫 `7za`，`command -v 7z` 失败会降级到 xz（仍可用，压缩率略低）。
- **动作**：装好后 `which 7z 7za`；若只有 `7za`，把脚本里 `command -v 7z` 改为 `command -v 7za`，或建软链。

### B5. ezB 周期交易"每月"的准确表达（中风险）
- **问题**：ezB 周期交易重复规则的具体参数（间隔/类型）需实机确认字段；方案写"每月"但没给 ezB 的周期表达式。
- **动作**：在 ezB Web 建周期交易时设置"每月 X 号"，记下参数；若需 n8n 调用 API 建，再补字段映射。

### B6. Vikunja recurring 任务生成新实例的标签继承（中风险）
- **问题**：`ezbookkeeping-poll` 靠 `#recur-<标识>` 标签匹配当月实例并自动勾掉。需确认 Vikunja recurring 完成后生成的新实例**继承**原任务的 `recur` 与 `#recur-<标识>` 标签，否则闭环断裂。
- **动作**：实机建一个 recur 任务，完成一次，观察新实例标签是否保留。

### B7. n8n 内部 URL 与 Webhook 接收（低风险）
- **问题**：Vikunja Webhook 目标 `http://n8n:5678/webhook/...` 依赖 Docker 内网 DNS（`appnet`）。若 n8n 容器名或网络名变，需同步改。
- **动作**：保持 compose 中服务名 `n8n`/`vikunja`/`ezbookkeeping` 不变。

- 原始需求未明确要子任务；Vikunja 原生支持子任务（Subtask），如需在终稿补充。

- 容器无 healthcheck、无宕机告警。若需要，可加 `healthcheck` 或 uptime 机器人（非必须）。
